# Office文書 → Markdown変換

## 目的

Office文書を、Gitで人間が気持ちよく保守できるMarkdownにする：本物の見出し階層、きれいな表、ファイル参照される図（図の形式はユーザーの指示か確認で決める）。

変換は**再構成**であって抽出ではない。
抽出は **office-docs-reader**スキルの仕事であり、このスキルはその出力から始める。
再構成とは、元の表やレイアウトの形を維持することではない。
内容を理解し、漏れなく、仕様書の文書として組み立て直すことである（基本方針は`references/conversion-rules.md`）。

## 入力

office-docs-readerが生成した抽出ディレクトリ：

```
<dir>/
  extracted.md     位置情報付きの忠実な抽出結果
  inventory.json   個数と警告（変換の契約）
  media/           抽出した画像
  work/shapes.json 図形・テキストボックスのテキストとアンカー（xlsx）
```

元ファイル（.docx/.xlsx/.pdf）しかない場合は、先にoffice-docs-readerを実行する。
バイナリから直接再構成してはいけない。

## 手順

### 1. 契約を読む

`inventory.json` を読み、セクション／シート、表、テキストを持つ図形、コメント、メディアファイル、グラフ、警告を把握する。
これらの個数が、最終Markdownが照合すべき対象である。

### 2. 書く前に構造を計画する

- Word：文書のスタイル／セクションから見出し階層を決める。
- PDF：論理構造がないため、フォントサイズ・太字・しおり（目次）から見出し階層を復元し、全ページに繰り返されるヘッダー・フッター・ページ番号を取り除く。
  詳細は変換ルールのPDF編（`references/conversion-pdf.md`）を参照。
- Excel：先に各シートを種別分類する（データ表／画面仕様／文章／図主体／表紙・履歴）。
  種別ごとに構造は異なる。
  `references/conversion-rules.md` を参照。
- 図の形式は、**ユーザーの指示か確認で決める**：ユーザーが形式を指示している場合はそれに従い、指示がない場合は勝手に決めず、変換前に「PNGのままにするか、drawio.svg（SVG）に変換するか」をユーザーへ確認する。
  図が多い場合は、図の一覧を示して一括で確認してよい。
  確認の際は判断材料を添える：箱・矢印・テキストでできた図（フロー図、画面遷移、状態遷移、構成図、組織図など）は、drawio.svg（diagrams.netのグラフを埋め込んだSVG）にすると変換後も編集できる。
  写真、スクリーンショット、高密度・複雑な図、データのグラフなど、描き直すと情報が落ちたり捏造になったりするものは、PNGのままを推奨として提示する。
  drawio.svg化する場合は、単純なノード／矢印の図には`scripts/make_drawio_svg.py` を使い、リッチな図は.drawioソースを作成してdiagrams.netからSVGにエクスポートする。
  PNGのままにする場合は、参照＋テキスト説明を付ける。

### 3. 再構成する

- 図形・テキストボックス・コメントのテキストは、それが属するセクションへ吸収する（アンカー位置が手がかり）。
  図形の自動名（「正方形/長方形15」）は除去し、意味だけを残す。
- セル結合のある表：**基本は結合値の伝播**でパイプ表にする（左上だけ残して他を空欄にしない）。
  結合が列幅調整などのレイアウト都合だけの場合は、物理的な列幅を捨てて**論理的な列に再構成**し、通常のパイプ表にする。
  **HTML表は既定では使わない**（結合の構造自体が意味を持ち、どうしても表せない場合に限り、理由を添えてユーザーに確認してから使う）。
  行や列を落とすことは決してしない。
- **罫線で図を表現している箇所は表にしない**：セルの罫線で枠やレイアウトを描いた図（方眼紙の構成図など）は図として扱い、形式（PNG／drawio.svg）はユーザーの指示か確認で決める。
- 暗黙の意味を明示する：意味を持つ色・グレーアウト・取り消し線・塗りはテキストにする（`<del>`、状態の列、注記）。
  装飾だけのものは落とし、報告で一度だけ触れる。
- 図表番号と相互参照を `media/` のファイルと整合させる。
  描き直した図はMarkdownの隣に `<name>.drawio.svg` として保存し、画像と同じように参照する（`![図1](<name>.drawio.svg)`）。
  verify.pyがそのリンクもチェックする。
- 最終ファイルは抽出ディレクトリに `<stem>.md` として書く（`extracted.md` は監査証跡として隣に残る）。

### 4. 検証する

```bash
python3 <skill>/scripts/verify.py <dir> [<stem>.md]
```

照合する：見出し数と元の章数、表の行列、配置した図形テキスト数＝棚卸しの図形数、コメントは全て配置済みか、落としたものは理由付きで明示、メディアファイルが全て参照されている、リンク切れがない、グラフ／SmartArtが、ユーザーの指示または確認で決まった形式（drawio.svg／PNG＋説明）で存在する。

### 5. 報告する

ユーザーに伝える：何を変換したか、何をdrawio.svgに描き直したか、何がPNG/PDFのままでその理由は何か、何を落としたか（ページレイアウト、色、ヘッダー・フッター）、そして判断した箇所すべて。
この報告のない変換は未完了である。

## GitHub Copilotでの使い方

`templates/convert-spec.prompt.md` を対象リポジトリの`.github/prompts/convert-spec.prompt.md` にコピーし、エージェントモードで `/convert-spec` を実行する。
このプロンプトが2スキルを順に駆動する（readerの抽出 → 本スキルの再構成 → 検証）。

## ルール参照

詳細ルール——Word固有の扱い、Excelのシート種別、結合セル、数式、非表示シート、検証チェックリスト全文——は`references/conversion-rules.md`（共通）にある。
形式ごとのルールは`references/conversion-docx.md`／`conversion-xlsx.md`／`conversion-pdf.md` に分かれているので、対象形式のものだけ読めばよい。
再構成の前に読むこと。
